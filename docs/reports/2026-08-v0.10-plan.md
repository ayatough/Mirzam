# After v0.9.0: what the field looks like, and what to build — August 2026

Two research passes run after the `v0.9.0` release — one over Marp (Marpit
3.2.2 / Core 5.0.1 / CLI 4.5.0, their trackers sorted by reactions), one over
Typst 0.15 with Touying 0.7 and Polylux 0.4, with a side glance at Slidev —
condensed into a plan. The framing question, set by the author: **match what
Marp and Typst ship as standard; widen the lead where Mirzam is already
ahead.** The [August survey](2026-08-market-survey.md) still stands; this
report is the delta since it, and the decisions taken from it.

## What moved in the field since the survey

- **Marp Core 5 shipped (2026-08):** Shiki as the default highlighter **with
  line-range highlighting** (```` ```js {2,4-5} ````), native Mermaid, MathJax
  v4, modular core. Marp CLI added an overview grid (v4.3) and experimental
  editable PPTX via LibreOffice (v4.1).
- **Marp has morph transitions.** The bespoke template morphs elements matched
  by `view-transition-name` across slides — PowerPoint-Morph-shaped, on the
  View Transition API. It is rough at the edges (their #510: an element named
  on one side only morphs badly), but it exists, which moves "carrying an
  element from one slide to the next" (W18) from differentiator to **parity
  item with a differentiation opportunity** — theirs is screen-only and dies
  in export; Mirzam's resting-state rule would keep the PDF whole.
- **Marp's most-reacted CLI issue is still open: handout PDF with notes**
  (#261, open since 2019, "Todo" on their roadmap). Their persistent wontfix
  cluster is CSS-free layout — columns, centering, percentage image sizing —
  which is exactly the ground the ASCII grid already owns.
- **Typst 0.15's HTML export is still experimental** and Touying closed its
  HTML issue as not-planned; every Typst web/PPTX route is rasterised. Its
  structural advantages remain scripting (data-driven decks), print-grade PDF
  (tagged, PDF/UA-1 since 0.14), and native math. Its animation model is
  still duplicated PDF pages.
- **Slidev** remains the web-native ceiling (Vue in slides, recording,
  Monaco) at the cost of a Node toolchain — a different lane, per the
  survey's non-goals.

## The queue, judged by the author's criteria

Each item scored on: dissatisfaction with today's behaviour, fit with what
Mirzam is, human+agent affinity, technical feasibility, licence, difficulty
(Sonnet-class = specified and checkable by tests; Opus-class = cross-cutting
or geometry/timing; Fable-class = the invariants are the work), and whether
it widens the audience.

**P0 — Code line highlighting and line numbers.** Marp and Slidev both ship
```` ```js {2,4-5} ````; Mirzam colours tokens and stops. For the
developer-talk audience this is the visible gap now that highlighting itself
landed. Fits the house (build-time, theme tokens, degrades to a plain
fence), trivially licensable (no new dependency: it is spans and CSS),
Sonnet-class, and audience-neutral-to-positive. W20 explicitly left it "a
later stream once the engine exists"; the engine exists.

**P0 — W18, carrying an element from one slide to the next.** Was the
roadmap's named gap; now also Marp parity. The differentiation is the
resting-state rule: Marp's morph exists only under the View Transition API
on screen, while Mirzam's two slides stay two complete slides — PDF intact,
JavaScript-off intact — with the move as pure runtime. All parts exist
(`{#id}` names elements; `annot.js` measures boxes against a scaled deck;
`anim.js` owns the page turn). Fable-class: separate DOM subtrees, a lift
layer that outlives both slides, backwards as good as forwards. No licence
question — it is our own runtime.

**P1 — PPTX export, staged.** Still the survey's largest unbuilt item and
the clearest audience-widener (the deck someone is *required* to submit as
`.pptx`). Stage 1 — slide images plus real speaker notes — is where Marp,
Slidev and Touying all stop, and is Opus-class plumbing (Chromium
screenshots the exporter already knows how to drive, plus a hand-written
OOXML zip; no dependency needed beyond a zip writer, licence clean). Native
text boxes stay the later differentiator. Not started this session because
it deserves a stream of its own with fixture-based OOXML tests.

**P1 — the VS Code extension starts `mirzam lsp`.** The server now
completes, hovers and jumps; the one editor with the preview extension does
not start it. Small, Sonnet-class, and it compounds the agent story.

**P2 — the rest of the unattended screen** (Ken Burns on `bg`, `mirzam
export video`, a loop progress hint). The dwell and media-wait halves
landed; these stay ordered as the roadmap had them.

**P2 — a scope between the deck and the pane** (slide- and section-level
attributes). Unlocked demand rises as dials multiply; unchanged from the
roadmap.

**P2 — `[span]{...}` across a source line.** Documented constraint, real
authoring papercut, Sonnet-class (paragraph-level transform that must keep
fences untouched).

**Deliberately still out**, reaffirmed against both research passes:
executable code cells (Slidev/Quarto's ground and their toolchain weight),
real-time collaboration and analytics (server products), WYSIWYG, and
fetching webfonts (a deck is one offline file). Tagged/accessible PDF stays
P3: Typst leads there and it is real, but it needs Chromium's print
pipeline to cooperate, which is a research task before it is a feature.

## Policies confirmed by the research

1. **Degradation is the moat, not a constraint.** Every fresh feature this
   session — `each` degrading to a readable data table, the handout printing
   from the same sections, dwell as an invisible comment — cost nothing to
   keep plain-Markdown-safe, and the research keeps finding competitors
   wedged on the opposite bet (Marp's fragments dying in export, Typst's
   subslide-per-pause PDFs).
2. **Agent affinity is now a scored axis in public comparisons.** The
   `check --format json` → LSP → skill-install chain is ahead of the field;
   keep every new feature reachable from that loop (each's `build.each`
   warnings, the LSP completing `each` fences, are this session's
   instances).
3. **When a competitor ships a differentiator of ours, answer in our
   grammar, not theirs.** Marp's morph is `view-transition-name` CSS; W18
   should stay `{#id}` + the resting-state rule. Marp's line highlight is
   fence-info syntax (```` ```js {2,4-5} ````) shared with Slidev/GitHub —
   that one *is* the grammar to adopt, because the convention is the value.
