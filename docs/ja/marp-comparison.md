# Mirzam と Marp の比較

> これは [docs/marp-comparison.md](../marp-comparison.md) の日本語訳であり、原文が正です。
> 2026-08 時点の両プロジェクトのスナップショットに基づきます。どちらも開発中のため、
> 個別の事実は古くなり得ますが、設計上の賭けの違いは安定しています。

Marp は Markdown スライドツールとして最も成熟した存在です。[Marpit](https://marpit.marp.app/)
(コアフレームワーク) → Marp Core (実用機能) → Marp CLI / VS Code 拡張という階層の
Node.js 製エコシステムで、2016 年から開発が続き、テーマ・テンプレート・CI 連携の
コミュニティ資産が豊富にあります。表面的には Mirzam とよく似ています — どちらも
プレーン Markdown を書き、`---` でスライドを区切り、テーマ CSS を当て、HTML と PDF を
出力します。しかし似ているのはそこまでで、両者は「何が文書に属するか」について
正反対の賭けをしています。

## 一言でいうと

**Marp の賭け**: レイアウトとデザインは *テーマ CSS* に属する。Markdown は内容だけを
持ち、見た目が欲しければ CSS を書く (あるいは書ける人のテーマを使う)。だから
フレームワークは最小限であり続けられる。Marpit は「事前定義クラスを持たず、純粋な
CSS によるスタイリングに焦点を当てる」ことを明示的な設計方針としています。

**Mirzam の賭け**: レイアウト・図・データ・アニメーションの順序は *文書そのもの* に
属する。だから ASCII で描くペイングリッド、CSV から生成されるチャート、文中の語と
チャートの棒を結ぶコネクタ、タイムライン DSL が、すべて Markdown ファイルの中に
(プレーンパーサではコードブロックに退化する形で) 書かれる。

この違いから、以下の相違点のほぼすべてが導出されます。

## 類似点

- プレーン Markdown がソース。git で diff でき、どのエディタでも開ける。
- `---` がスライド区切り。frontmatter でデッキ全体の設定。
- テーマは CSS。カスタム CSS を差し込める。
- HTML と PDF を出力。発表者ノート、ページネーション、数式をサポート。
- 「Markdown を汚さない」ことへの配慮。Marp はディレクティブを HTML コメントに逃がし、
  Mirzam は全拡張がプレーンパーサでコードブロックや段落に退化することをテストで強制する。

## アーキテクチャの違い

| | Marp | Mirzam |
|---|---|---|
| 実装 | Node.js + markdown-it | Rust (ネイティブ + WASM 同一コア) |
| HTML 変換 | Node ランタイム必須 | 単一バイナリ、依存なし |
| PDF / 画像 | Chrome/Edge/Firefox を CDP で駆動 | 同じ HTML を Chromium で印刷 (PDF のみ) |
| PPTX | あり (スライドをラスタ画像化、編集可能出力は実験的) | 未実装 (計画中) |
| エディタ連携 | VS Code 拡張 (プレビューは全デッキ再変換) | VS Code 拡張 + ブラウザ playground (WASM で CLI と同一出力) |
| 増分ビルド | なし (ファイル単位で再変換) | スライド単位キャッシュ、編集ごとに再レンダリングは厳密に 1 スライド |

## Markdown の書きやすさ

**単純なデッキでは Marp のほうが覚えることが少ない。** タイトル + 箇条書き + 画像の
デッキなら、Marp は frontmatter に `marp: true` を書く以外ほぼ素の Markdown です。
`![bg right](img.png)` のような画像ディレクティブも簡潔で、既存の慣習として広く
知られています。

**レイアウトが欲しくなった瞬間に逆転する。** Marp で 2 カラムやカード配置をするには
テーマ CSS を書くか、Markdown に生の HTML (`<div class="columns">`) を埋め込むことに
なります。つまり「Markdown の書きやすさ」はテーマ作者の CSS 力に外部化されている。
Mirzam では同じことが文書内で完結します:

````markdown
```pane
+--------+--------+
| left   | right  |
+--------+--------+
```

::: pane left
...
:::
````

列幅は境界間の文字数、行高は行数。描いた図がそのまま仕様であり、CSS も HTML も
登場しません。チャート (CSV から)、図形、コネクタ、注釈、アニメーションも同様に
フェンスブロックで文書内に留まります。

もう一つの違いは *退化の保証* です。Marp のディレクティブ (HTML コメント) は他の
ツールでは単に消えますが、`![bg](...)` は「壊れた画像」として現れます。Mirzam は
「全拡張がプレーン CommonMark でコードブロック・リテラルに退化する」ことを CI の
テストで強制しており、`--split h2` と合わせて「既存の README が無編集でデッキになる」
方向に全体が設計されています。

## レンダリングの速さ

Mirzam が構造的に有利です。計測値 (`docs/roadmap.md`):

| デッキ | フルビルド | 1 スライド編集 |
|---|---:|---:|
| 20 スライド | 4.5 ms | 0.4 ms |
| 500 スライド | 75.6 ms | 3.2 ms |

Rust の単一バイナリで、HTML 出力にブラウザも Node も不要。watch モードは変更された
`<section>` だけをクライアントにパッチします。Marp は Node 起動 + ファイル単位の
再変換で、PDF/PPTX/画像には実ブラウザの起動が必要です。公開ベンチマークはありません。

ただし正直に言えば、**30 枚程度の普通のデッキでは両者とも「十分速い」**。この差が
効くのは、大規模デッキ、エディタ内プレビューの応答性 (WASM でキーストローク毎に
再レンダリングできる)、そして CI でデッキを毎コミット検証するワークフローです。

## アニメーション

驚かれた通り、Marp のアニメーションは実用段階です — ただし対象範囲が違います。

**Marp**: View Transitions API による *スライド間* トランジション。33 種組み込み +
CSS でカスタム定義でき、ブラウザネイティブで滑らかです。スライド内は fragmented list
(`*` 箇条書きの逐次表示) まで。要素単位の振り付けは CSS を自分で書く領域です。

**Mirzam**: スライド間トランジションに加え、スライド *内* のタイムライン DSL を持ちます
— `[click 1] .callout : slide-in 400ms ease=spring(1,180,20)`、文字単位の stagger、
`after #id +100ms` によるチェーン。スプリング曲線はビルド時にサンプリング済みです。
さらに「文書に属する `anim`」と「上演にのみ属し、エクスポートには決して入らない
`effects` (紙吹雪・集中線・弾幕など)」を区別し、アニメーションの有無に関わらず
JS なし・PDF では全内容が露出することを保証します。

## Marp が優位な点

事実として認めるべきものです:

- **成熟度とコミュニティ**: 10 年分の実績、テーマ資産、Stack Overflow の回答、
  CI アクション、他ツールからの移行ガイド。
- **PPTX 出力**: 「上司が PowerPoint でしか受け取らない」職場では決定打になる。
  Mirzam は未実装。
- **エコシステムの拡張性**: markdown-it プラグインで Mermaid その他を差し込める。
- **VS Code 拡張の普及**: インストール数が桁違いで、導入の摩擦が小さい。
- **少ない概念数**: 覚えるべき独自記法が少なく、単純な用途では学習コストが最小。

## Mirzam が優位な点

- **レイアウトが文書内で完結する** (ASCII ペイングリッド)。Marp の空白地帯そのもの。
- **データからのチャート生成 + 安定 ID**: 文中の語からチャートの特定の棒へコネクタや
  注釈を張れる。スクリーンショット貼り付けでは原理的に不可能。
- **プレビューと PDF の一致が構成上保証される**: 同じ HTML を印刷し、アニメーションは
  最終状態でレイアウトされ、注釈は PDF にも届く。
- **単一自己完結 HTML**: 画像・動画・フォントまでインライン化され、メールで送れる。
- **プレゼンター画面が同一ファイル**: `?presenter=1` で開き直すだけ。サーバ不要。
- **速度と増分性**: 上記の通り。
- **検証可能性**: `check-layout` がはみ出し・重なり・死んだ参照を CI で検出する。
  「デッキをテストできる」のは他にない性質。

## 差別化の提案

「かなり似たものになるのでは」という懸念への答え: 共有部分 (Markdown + `---` + テーマ
CSS) は両者の最も薄い層であり、Mirzam の中核 (レイアウト・データ・注釈・検証) は
Marp が設計思想として *持たないと決めている* 領域です。Marpit は最小性を明示的な
方針にしているため、この空白は追随されにくい。その上で:

1. **「文書 → デッキ」を正面に掲げる**。`--split h2` + 退化保証により、README や設計
   メモが無編集でデッキになるのは Mirzam だけ。Marp は「スライドを書く」ツール、
   Mirzam は「書いたものがスライドになる」ツール、という対比は明確に立つ。
2. **データドリブンなデッキ**。CSV 更新 → チャート・変数・注釈が追従、という
   「毎週の報告デッキ」ワークフローは Marp では成立しない。
3. **検証できるデッキ**を売りにする。コーディングエージェントがデッキを書き、
   `check-layout` が CI でレイアウト崩れを落とす — エージェント時代のスライド基盤
   という位置づけは Marp にない。
4. **PPTX 出力の欠落を塞ぐ**のは採用面で最優先度が高い。ロードマップ通り。
5. **テーマの数で戦わない**。Marp のテーマ資産には追いつけないので、「トークンだけの
   テーマ + 両モード対称性の保証」という質の違いで語る。

## 要約

| 観点 | 優位 |
|---|---|
| 単純なデッキの学習コスト | Marp |
| レイアウト制御 (CSS/HTML なしで) | Mirzam |
| ビルド・プレビュー速度、増分性 | Mirzam |
| スライド間トランジション | ほぼ同等 (Marp はブラウザネイティブ、Mirzam は DSL) |
| スライド内アニメーション | Mirzam |
| 出力形式の広さ (PPTX 等) | Marp |
| エコシステム・実績 | Marp |
| データ連携 (チャート・変数・注釈) | Mirzam |
| PDF とプレビューの一致、退化保証、CI 検証 | Mirzam |

Mirzam は「Marp の代替」ではなく、Marp がテーマ CSS の外に置いたもの — レイアウト、
データ、動き、検証 — を文書の中に取り込んだツールです。似るのは入口だけで、
深くなるほど離れていきます。
